# ADR-0002：P0 阶段下架 news-insight

- 状态：已接受
- 日期：2026-10-17
- 关联：ADR-0001、开发计划 v1.9 §4 P0a（原含「恢复 news API」）

## 背景

P0a 原计划包含「恢复 news-insight API（依赖→启动→`/healthz` 200→supervisord 守护→连续 3 次探测）」。实际盘点结果与该假设不符：

| 项 | 实测 |
|---|---|
| 进程 | `8000` 端口无监听；服务器上仅 nginx 在跑 |
| 数据库 | **postgres / mysql 均未安装、未运行**，只有一个 368KB 的 `insightpulse.db` |
| 依赖声明 | `requirements.txt` 写 `psycopg2-binary`，与 sqlite 文件矛盾 |
| 配置 | `.env` 只有 `DASHSCOPE_API_KEY / DATABASE_URL / PROJECT_NAME / API_V1_STR`，**没有新闻源 Key**（开发计划假设的「天行数据」并不存在） |
| 日志 | `backend.log` / `gunicorn.log` 最后写入停在 2026-01 |

结论：这不是"服务挂了重启一下"，而是一个**依赖缺失、数据源不明、至少停摆九个月**的系统。

## 决策

P0 阶段**下架 news-insight**：

1. 不迁入 monorepo，不进入镜像，不占 `8000` 端口。
2. `nginx → Caddy` 割接时删除 `/api/` 反代规则。
3. `/healthz` 只聚合 electro API，不依赖 news。
4. 服务器上 `/var/www/insightpulse` 与 `apps/news-insight` **不删除**，原样保留，随时可回。
5. 门户与粒子系统保留（纯静态，零维护成本）。

## 理由

- **恢复成本 > 收益**：需重建数据库、跑 alembic 迁移、确认数据是否还有价值、重新对接新闻源，保守估计半天到一天。而这些工作对作品集没有增量——面试官不会因为一个聚合新闻站加分。
- **P0 的目标是"提交即上线跑通"**，不是"复活所有历史模块"。把一个死系统塞进镜像，会让健康检查、部署脚本、回滚判断都变复杂，直接违反"P0 只做骨架"的原则。
- **保留退路**：代码和数据都在，未来若要做，另开分支即可，不是不可逆删除。

## 后果

**正面**

- P0a 工期减少 0.5–1 天。
- 镜像更小、启动更快、健康检查语义更清晰（只有一个后端要探）。
- 少一个"数据源不明"的合规隐患。

**负面**

- 站点暂时失去"新闻洞察"这个模块，门户上的对应入口需要加"暂停服务"标识或先摘掉。
- 若将来恢复，需要重新评估：数据是否还值得迁、新闻源用哪家、要不要直接用 RAG 重写。

**验收标志**

- 镜像内无 8000 监听；`/api/news/*` 返回 404 而非 502。
- `/healthz` 返回 `{"status":"ok","checks":{"electro":"ok"}}`（不含 news）。
- 门户页面无死链（指向 news 的入口已处理）。
